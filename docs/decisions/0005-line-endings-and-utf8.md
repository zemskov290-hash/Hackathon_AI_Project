# ADR 0005. LF в репозитории и UTF-8 на выводе

- Статус: принято
- Дата: 2026-11-04

## Контекст

На Windows с `core.autocrlf=true` git при выгрузке меняет LF на CRLF. sha256 считался от сырых байт, поэтому учебные источники переставали сходиться с уже записанным хешем, хотя текст был тот же. Отдельно консоль cp1251 или cp866 не кодирует всё сообщение целиком: `print` падает с `UnicodeEncodeError`, stdout пустой, а `python3` на этой машине оказался заглушкой Microsoft Store. Команда `python` указывает на Python 3.13.

## Решение

Два независимых барьера для перевода строк. `.gitattributes` задаёт `* text=auto eol=lf`, чтобы рабочая копия оставалась с LF и на Windows. Для текстовых суффиксов (`.md`, `.txt`, `.csv`, `.json`, `.jsonl`) `check` и `add-source` считают sha256 после замены CR на LF. Двоичные файлы хешируются как есть: подмена байт в pdf была бы порчей, а не нормализацией.

Вывод CLI и `read_material.py` в начале процесса переключается на UTF-8 (`reconfigure`, на Windows ещё кодовая страница консоли 65001). Тесты читают stdout как UTF-8 и зовут интерпретатор через `sys.executable`. Хуки — скрипты Python; оболочечные обёртки сначала ищут `python`, потом `python3`.

## Последствия

Уже склонированный пример проходит `check` без переписывания файлов. Новые файлы проекта пишутся с LF. Цена нормализации: хеш текста не равен хешу байт, если в файле остались CR. Для двоичного источника это не применяется. Кто смотрит хеш снаружи, должен нормализовать текст так же.
